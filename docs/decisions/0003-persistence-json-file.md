# 0003 · 配置持久化：应用沙箱单 JSON 文件；私钥明文随配置存（依赖沙箱隔离）

- 状态：**已决定**（2026）
- 关联：[specs/privacy-security.md](../specs/privacy-security.md)、[specs/config-format.md](../specs/config-format.md)、上游 `ui/.../configStore/`

## 背景

需要定两件事：**隧道配置的存储介质**（Preferences / 关系型数据库 / 文件）与
**私钥的存放方式**（明文随配置 / HUKS 密钥库）。spec 已定两条硬约束：

1. 「查看私钥」「导出配置」均要求能向用户呈现**明文私钥**（锁屏认证后）——
   私钥在存储侧必须是可还原的；
2. 「所有隧道配置（含私钥）仅保存在本机应用内」。

## 候选方案与取舍

**存储介质**：

| 方案 | 结论 | 理由 |
|---|---|---|
| Preferences（KV） | ❌ | 面向小型偏好项；隧道列表是结构化集合（名称/接口/多 peer/ AllowedIPs），KV 下要自己做序列化与并发控制，无收益。 |
| 关系型数据库（RDB） | ❌ | 上游 Android 用 Room 属历史惯性。本项目无复杂查询（列表+按名读取）、数据量小（数十条）、无多端同步；引入 RDB 只增加 schema 迁移负担。 |
| **应用私有目录 JSON 文件** | ✅ | 数据模型天然是文档形（一份隧道 = 一个文档）；读写即整体序列化，配合「临时文件 + rename」原子替换即可避免半写损坏；对本地单测友好（纯序列化逻辑不进 @kit）。 |

**私钥存放**：

| 方案 | 结论 | 理由 |
|---|---|---|
| HUKS 不可导出密钥 | ❌ | 与 spec 直接冲突：私钥不可导出则「查看私钥/导出 .conf」无法实现。协议私钥必须能还原为明文，此路不通。 |
| **明文随配置文件存，依赖应用沙箱隔离** | ✅ | 与上游 WireGuard-Android 的威胁模型一致（配置明文存私有目录，靠系统沙箱保护）。spec 的保护语义是「访问门槛」（锁屏认证）与「不出日志」，而非静态加密。 |
| HUKS 包裹 DEK 加密配置文件（密钥不可导出、但配置可解密还原） | 暂缓 | 技术上与导出功能兼容（DEK 可解密出明文再导出），是真实的安全增强；但增加 HUKS 可用性分支（设备无锁屏凭证时的行为、密钥随备份恢复等）与真机验证面。**列入后续增强候选，不进 v1**。 |

## 决策内容

1. **存储布局**：应用私有 files 目录下 `tunnels.json`（全量隧道集合）+
   原子写入（写 `tunnels.json.tmp` → flush → rename）。读取失败按空列表处理并保留损坏文件备份。
2. **序列化边界**：JSON 读写与 diff 逻辑放纯 ArkTS 模块（`repo/`），不 import `@kit`，
   文件 I/O 做成注入式接口 → 本地单测可全覆盖序列化/损坏恢复逻辑。
3. **私钥威胁模型**：依赖系统应用沙箱；保护手段是 spec 定义的**访问控制**（查看/导出前锁屏认证）
   与**日志脱敏**（私钥/预共享密钥不进 hilog 与导出日志）。
4. **后续增强候选**：HUKS 包裹 DEK 静态加密，单独立项评估（需先解决无锁屏凭证设备的行为定义）。

## 后果

- 正面：实现最简、可测性最好、与 spec 逐条对齐；原子写保证崩溃不丢配置。
- 负面：拿到设备 root/备份数据即可读私钥 —— 与上游一致的风险敞口，已在 spec
  「本地保存承诺」的用户告知层面覆盖。
