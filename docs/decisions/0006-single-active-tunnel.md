# 0006 · 隧道模型：多配置、单激活，互斥由 backend 层保证

- 状态：**已决定**（2026）
- 关联：[specs/tunnel-connection.md](../specs/tunnel-connection.md)、[0004 进程通信](0004-ui-vpn-ipc.md)

## 背景

上游支持任意多隧道配置，但同时只有一条处于 UP。鸿蒙系统层同样只允许一条 VPN 连接。
需确定本项目的并发模型：是否允许多隧道同时激活。

## 决策内容

1. **多配置、单激活**：隧道列表数量不限，但同时至多一条 UP——与上游语义一致，
   且被系统约束强制（即使想多激活也做不到）。
2. **互斥保证放在 backend 层，不靠 UI 自律**：
   - ArkTS backend 维护「当前激活隧道名」单一真源；
   - 发起连接 B 时若 A 已激活：先 stop A（等 `onDestroy` 完成/状态事件确认）再 start B——
     对齐 spec「切换隧道：先断开 A 再连接 B，期间两个开关均禁用」；
   - 不依赖「系统拒绝重复启动」作为互斥手段（那只是兜底错误文案场景：
     「系统同时只允许一条 VPN 连接，请先断开其他 VPN 后重试」——该提示面向
     **其他应用**占用 VPN 的情形）。
3. **模型层状态**：每条隧道持有独立 `State`，但不变量「至多一条 UP/TOGGLE」
   由 backend 在状态迁移入口统一校验；UI 只读快照（0004），不做互斥判断。
4. **C 数据面按单实例设计**：原生层同一时刻只承载一条隧道的会话表与转发线程，
   不做多隧道资源隔离——换隧道即整体 stop/start 原生实例，简化内存模型。

## 后果

- 正面：模型与系统约束同构，无并发数据面复杂度；spec 的切换/编辑重连语义有直接落点。
- 负面：频繁切换隧道有 stop→start 的固定开销（约一次握手往返）→ 可接受，
  spec 已定义切换为显式用户操作。
